# GPTBot got 429 at the host edge while robots.txt allowed it

The web host's edge answered GPTBot with HTTP 429 and let the other AI crawlers we saw straight through.

It was the same site with the same robots.txt, and that file allowed GPTBot the whole time. The only variable was the user agent, and the block sat at the web host's edge, in nothing we had written.

We found this in September 2026. Until then we treated robots.txt as the switch that decides which crawler gets in. The host, CDN or firewall in front of the site gets a vote too, and it never reads robots.txt before casting it.

So a screenshot of robots.txt cannot prove AI assistants can reach a site. The file can say yes while the edge answers one crawler with 429 (too many requests) and waves the rest through.

If a client asks whether AI assistants can reach their site, that screenshot is the easy answer. It is also the answer we would have given before September.

What we would check on any site, ours or a client's:

1. Pull raw server or CDN logs, where crawler requests are actually recorded. If the block sits at the edge, the origin server may never see the request, so read the logs from the layer that answers first.

2. Filter by user agent: GPTBot first, then each AI crawler you care about. Do it one agent at a time, because a combined view can bury one crawler's problem inside everyone else's normal traffic.

3. Compare status codes per agent. A run of 429s for one agent and normal responses for the others is the pattern we hit. A single 429 can be ordinary rate limiting. The split between agents is what gave it away.

4. Then open the host's bot and rate limit settings, because that is where our block lived.

5. Keep a note of what each agent got back, so the next check has something to compare against.

When did you last look at the status codes your host returns to AI crawlers, rather than the robots.txt?
