# GPTBot got a 429 even though robots.txt allowed it

GPTBot/1* requests to our site were getting HTTP 429. Our robots.txt allowed GPTBot the whole time.

We found it in September 2026. The block sat at our web host's edge, outside every file we had written.

On the same site with the same robots.txt, other AI crawlers passed through fine. The only variable was the GPTBot user agent.

We had treated robots.txt as the switch for AI crawlers. It is one layer. A host, CDN or firewall can answer a bot before robots.txt is ever read, and a 429 ("too many requests") looks like routine rate limiting, so nobody flags it.

That is what kept it quiet for us. Nothing looked broken, and the file we thought controlled access said yes.

Analytics will not show it either. Flowra's AI traffic report reads GA4 referrers, so it only counts visits that arrive. A crawler turned away at the edge leaves nothing there.

What we check now on any site we run SEO for:

1. Raw server or edge logs filtered by AI crawler user agents. If you do not have access to edge logs, ask the host for them.
2. The status code each crawler got. 200 is in. 403 or 429 means something upstream said no.
3. Each crawler on its own. Others passing told us nothing about GPTBot, so we no longer read one good result as a pass for the rest.

On client sites where the developers own the host and firewall, whoever runs SEO may never see those settings.

If a client's AI referral traffic looks flat, this is a cheap thing to rule out before you rewrite a single page. A crawler that never got a 200 never saw the old version either.

When did you last check what your host returns to GPTBot, rather than what robots.txt says?
