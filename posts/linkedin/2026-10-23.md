# GPTBot got a 429 while robots.txt said allow

GPTBot requests to the site: HTTP 429.
Other AI crawlers on the same site: let through.

Same site, same robots.txt, and that file allowed GPTBot. The only variable was the user agent: the web host was rate limiting anything matching GPTBot/1* at the edge.

We ran into this ourselves in September 2026.

Our first assumption was the usual one. If robots.txt says allow, the crawler gets in and the audit box is ticked.

That file only covers what you invite. It says nothing about what your host, CDN or firewall does with the request once it arrives. The edge in front of your site makes its own decision, whatever robots.txt says.

A 429 also means "too many requests", which reads like a rate limit and not a block, so it is easy to scroll past in a log. If your monitoring only flags 403s and 5xx errors, a 429 will not register as a crawl problem at all.

What we check now, for each AI crawler user agent:

1. The status code the server actually returns, from raw access logs. Filter by user agent and put GPTBot next to the other AI crawlers hitting the same URLs: a 200 for one and a 429 for the other is the pattern to look for.

2. Whether the host or CDN has any bot or rate limit rules turned on. If the content team has no login for the hosting dashboard, ask whoever does.

3. The robots.txt line, last, because in our case it was the one thing that was right.

If your team is putting work into showing up in ChatGPT answers, run this check before the next content push. It is short.

When did you last look at the status code your host returns to GPTBot, and not only at what robots.txt says about it?
